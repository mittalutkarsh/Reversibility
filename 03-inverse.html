03 / THE MATHS

Why one inverts and one does not

midpoint   pl−1 = pl+1 − 2h·f(pl)     f is evaluated at a state we already hold
euler       pl = pl+1 − h·f(pl)         f is evaluated at the thing we are solving for Both come from rearranging the forward rule. The difference is which state f needs.

The algebra, one step at a time

Midpoint inverts

rearranging the forward rule
forward     p[l+1] = p[l-1] + 2h·f(p[l])

subtract    p[l+1] - 2h·f(p[l]) = p[l-1]

flip        p[l-1] = p[l+1] - 2h·f(p[l])

walking down we already hold p[l+1] and p[l].
f needs p[l], which is in hand. Nothing is unknown.

Euler does not

the same rearrangement
forward     p[l+1] = p[l] + h·f(p[l])

subtract    p[l+1] - h·f(p[l]) = p[l]

flip        p[l] = p[l+1] - h·f(p[l])
                                    ^^^^
            the unknown appears on BOTH sides.

This is an implicit equation

To find p[l] you need f(p[l]), and to compute that you need p[l]. There is no closed form.

You could solve it iteratively — a fixed-point or Newton method per layer. But that is an approximation with its own tolerance, not an inverse, and it would cost more forward evaluations than the activation memory it saves. The whole point would be lost.

What a ULP is, and why it matters here

fp32 spacing for a number in [1, 2) = 2−23 = 1.19209e−07 ULP means "unit in the last place" — the gap between one representable float and the next. It is the smallest error any calculation can have.

Floating point cannot store every number. Between 1 and 2, fp32 stores values spaced 2⁻²³ apart. An answer off by one ULP is as correct as fp32 allows.

The first recovered state is off by exactly one ULP. 1.192e−07 is precisely 2⁻²³, and the state's largest value is 1.32 — which sits in [1, 2) where that spacing applies. It is a single rounding.

Four steps later it is 8 ULP, and the growth is decelerating: 5.00×, then 1.34×, then 1.20×. That is roundoff accumulating and flattening, not error being amplified.

The test that separates the two failure modes

Run the same check in bf16, which has an 8-bit mantissa instead of fp32's 23. Machine epsilon changes by a factor of 2¹⁵ = 32,768.

Same check, two precisions
Variantfp32bf16RatioWhat that means
midpoint9.574e−071.263e−0213,192× error scales with precision → rounding
euler6.531e−016.554e−011.0035× error ignores precision → the map is wrong

This is the cleanest evidence in the whole experiment

Midpoint's error moves by 13,192× when the float grid gets 32,768× coarser — same order, so it is the grid. The rule is exact; only the arithmetic is approximate.

Euler's error is identical to three significant figures across that same change. Precision is irrelevant because the formula itself is wrong. No amount of extra bits would help.

The gate that nearly let euler through

The original check flagged any single step growing more than 10×. Euler grows a steady 1.4× per layer, so it was waved through as "not growing" — only the magnitude check caught it.

the tightened rule
clamp errors to an 8-ULP floor, dtype-aware
  fp32: 8 × 2^-23   bf16: 8 × 2^-8

flag 3 or more consecutive increases whose total exceeds 3×

  euler    fp32   4 increases, 4.57×  → GROWING
  euler    bf16   4 increases, 4.60×  → GROWING
  midpoint fp32   1 increase,  1.00×  → not growing
  midpoint bf16   none above floor      → not growing

Below the floor, "growth" is the float grid rather than the rule — which is why the floor has to be there.

Carry this forward: midpoint's inverse evaluates f at a state already held, euler's evaluates it at the unknown; the bf16 test proves one error is rounding and the other is a wrong formula.
