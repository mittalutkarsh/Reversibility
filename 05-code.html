05 / THE BUILD

The code

five changes, in order of dependency 1. move the norms inside f   2. add the three combination rules   3. the autograd.Function   4. the layer-0 bootstrap   5. the blend at readout

Every change below is real code from the project. The annotations say what each one buys, and why it could not have been done another way.

1. Move the layer norms inside f

before — two explicit residuals
def forward(self, x):
    x = x + self.attn(self.ln1(x))
    x = x + self.mlp(self.ln2(x))
    return x
after — one function f
def forward(self, x):
    # returns the UPDATE, not the new state
    a = self.attn(self.ln1(x))
    m = self.mlp(self.ln2(x + a))
    return a + m

What it buys: the stack can now choose how to combine f(x) with previous states. Before, the combination was hard-coded inside the block.

This is a refactor, not a different model

With f(x) = attn(ln1(x)) + mlp(ln2(x + attn(ln1(x)))), the rule x + f(x) is algebraically identical to the original two-step block. The baseline computes exactly what it computed before.

That matters: if the refactor changed the model, the baseline would not be a valid control.

2. The three combination rules

model.py — the stack
def forward(self, idx):
    x = self.embed(idx)

    if self.variant == "baseline":
        for blk in self.blocks:
            x = x + blk(x)                      # one chain

    elif self.variant == "euler":
        for blk in self.blocks:
            x = x + self.h * blk(x)           # one chain, scaled

    elif self.variant == "midpoint":
        prev = x                                # p[l-1]
        x = x + self.blocks[0](x)           # bootstrap -> p[1]
        for blk in self.blocks[1:]:
            prev, x = x, prev + 2 * self.h * blk(x)
        x = self.blend * x + (1 - self.blend) * prev

The highlighted line is the whole rule. prev, x = x, ... is a simultaneous assignment — the new state is built from the old prev, two layers back, while x slides down to become the new prev.

why the tuple assignment matters
wrong:
  prev = x                          prev is now p[l]
  x = prev + 2h*blk(x)              adds to p[l], not p[l-1]  → this is euler

right:
  prev, x = x, prev + 2h*blk(x)     both read the OLD values first

3. The autograd.Function

This is where the memory is actually saved. PyTorch would otherwise keep every intermediate tensor for the backward pass — writing a custom Function is how you tell it not to.

reversible.py — forward
class MidpointRev(torch.autograd.Function):

    @staticmethod
    def forward(ctx, x, blocks, h, *params):
        with torch.no_grad():                # no graph is built
            prev = x
            x = x + blocks[0](x)
            for blk in blocks[1:]:
                prev, x = x, prev + 2*h*blk(x)

        ctx.save_for_backward(x, prev)      # ONLY the final pair
        ctx.blocks, ctx.h = blocks, h
        return x, prev

The two lines that do the work

torch.no_grad() stops PyTorch recording the graph, so no intermediates are retained.

save_for_backward(x, prev) keeps two tensors, regardless of depth. A standard forward would have kept roughly 5 × layers of them.

reversible.py — backward
    @staticmethod
    def backward(ctx, g_x, g_prev):
        x, prev = ctx.saved_tensors
        h, blocks = ctx.h, ctx.blocks
        g_hi, g_lo = g_x, g_prev

        for l in reversed(range(1, len(blocks))):
            mid = prev                          # this is p[l]

            # one recomputation, WITH a graph this time
            with torch.enable_grad():
                m = mid.detach().requires_grad_(True)
                out = blocks[l](m)

            # job 1: rebuild the state below
            with torch.no_grad():
                below = x - 2*h*out

            # job 2: push gradient through that same graph
            grads = torch.autograd.grad(out, [m] + params_of(blocks[l]),
                                        grad_outputs=g_hi * 2*h)
            g_lo = g_lo + grads[0]            # through f
            accumulate(blocks[l], grads[1:])

            x, prev = mid, below              # slide down
            g_hi, g_lo = g_lo, g_hi             # identity path: exact

Three things worth reading closely:

The non-obvious lines
LineWhy it is written that way
mid.detach().requires_grad_(True) starts a fresh, one-layer graph. Without the detach, autograd would try to walk back into the forward pass — which no longer exists.
below = x - 2*h*out the inverse from page 03. Under no_grad, because this is reconstruction, not a gradient path.
g_hi, g_lo = g_lo, g_hi the identity path needs no computation at all — the gradient passes through unchanged, so the two accumulators simply swap roles.

4. The layer-0 bootstrap

the special case, and why it is safe
prev = x                        # p[0]
x = x + blocks[0](x)            # p[1] — an ORDINARY residual

The midpoint rule needs p[-1], which does not exist. Layer 0 runs as an ordinary residual block to manufacture the second state.

Why this does not break reversibility

The bootstrap is never inverted. The backward walk stops at layer 1, and p[0] falls out of layer 1's inverse rather than layer 0's.

So the choice affects which function the stack computes, not whether it can be run backward. It still carries gradient, through both its identity and its f path.

5. The blend at readout

one line, at the end of the stack
x = self.blend * x + (1 - self.blend) * prev    # blend = 0.5

Midpoint carries two interleaved streams — even states feed even, odd feed odd. They can drift apart, and averaging the final pair is the standard fix.

It costs nothing. Both states are held anyway, so this is one multiply-add on a single tensor. Unused for baseline and euler, which have a single stream.

One more change, made before run 04

before — a bug
VAL_TOKENS = VAL_BATCHES * batch * BLOCK
# at batch 32: 655,360 tokens
# but val.bin holds only 500,000
after
VAL_TOKENS = 163_840   # fixed
# identical for every run,
# independent of batch size

What this would have cost

Run 04 uses batch 32, so its validation set would have been four times larger than runs 01 to 03 — and would have wrapped past the end of val.bin, sampling overlapping regions.

The final losses would not have been comparable, which is the entire purpose of run 04. Caught before launch; the micro-batch builder was then verified to emit byte-identical batches at both batch sizes.

Carry this forward: the memory saving comes from two lines — no_grad in the forward and save_for_backward(x, prev) — and everything else exists to make those two lines correct.
