07 / THE EVIDENCE

The batch ceiling

the ceiling is the largest batch where throughput has not collapsed Not the largest that runs. On unified memory there is no clean out-of-memory error — the run keeps going and becomes catastrophically slow instead.

Why a Mac does not simply fail

On a discrete GPU, asking for too much memory raises an error. On Apple Silicon the GPU shares system RAM, so the operating system starts swapping — writing memory to disk to make room — and the run continues at a fraction of the speed.

That makes "maximum batch" a judgement, not a fact

This machine: 16 GB total, 3.28 GB free at sweep start, and a GPU allocator budget of 11.84 GB. Batch 80 "runs" — at one step per 273 seconds.

How swapping was detected

macOS keeps a counter of pages written to disk. Sampling it before and after each batch's subprocess gives a direct measurement rather than an inference from timing.

The trap that nearly chose batch 80

Three rows completed exactly one step

At n = 1, mean = median = p90, so mean_over_median comes out as a perfect 1.000 — which reads as a flawlessly quiet run.

The first analysis duly reported "largest batch with mean/median < 1.3: 80". That is a configuration managing one step per 273 seconds.

A MIN_SAMPLES = 10 guard now suppresses dispersion statistics below ten samples. The median is kept — one measured step is still a real duration, and at 165 to 278 seconds it is damning on its own.

This is worth generalising. A statistic that measures spread is meaningless when there is nothing to spread. Any automated threshold needs a minimum-sample guard, or it will happily recommend the worst option available.

Throughput never improves with batch

10,246 → 9,960 → 9,884 → 9,488 tokens/s   across batches 8 to 32 Monotonically down, entirely inside the healthy region.

On a discrete GPU a larger batch usually helps, by filling arithmetic units that were idle. Here there were none idle: a 20M model on this device is memory-bandwidth-bound long before it is compute-bound.

A larger batch buys headroom, not speed. That shapes the whole of the next page.

One full doubling of batch size. But notice the saving shrinking: 51.8% at batch 8, only 20.0% at batch 16.

Why the saving shrinks

Reversibility removes layer activations. It does not touch the output head, which is batch × 1024 × 8192 × 4 bytes — 268 MB per copy at batch 16, with three copies live.

As batch grows the head comes to dominate the peak, so the fraction reversibility can remove falls.

Carry this forward: the ceiling is where throughput collapses rather than where allocation fails, reversibility bought one doubling, and on this machine a bigger batch buys headroom rather than speed.
