08 / THE EVIDENCE

Better per step, worse per token

at step 1,526   batch 32 is 0.18 ahead
at 50M tokens  batch 32 is 0.32 behind Same model, same data, same schedule. Run 03 at batch 8, run 04 at batch 32.

Run 04 was supposed to be the payoff: reversibility freed enough memory to reach batch 32, so train there and see what it buys. It finished worse. But reading that as failure misses what happened.

Worse per token. Better per step. Both true, and neither is the whole story on its own.

Run 03's value at step 1,526 is interpolated between its measured points at steps 1,399 (2.3003) and 2,599 (2.0277).

Why a bigger batch helps each step

error in the averaged gradient ∝ 1 / √batch Each sample gives a noisy estimate of the true gradient. Averaging more of them cancels more of the noise.

Suppose the true gradient for some weight is 1.0, and each training sample gives an estimate scattered around it with a spread of 3.0. Average 8 of them, then average 32:

simulated, 20,000 trials each
averaging  8 noisy gradients   mean error  0.8413
averaging 32 noisy gradients   mean error  0.4243

ratio  0.8413 / 0.4243  =  1.98
√(32/8)                =  2.00

four times the batch, half the gradient error.

So each update at batch 32 points more accurately downhill. That is the 0.18 advantage per step.

Why it loses anyway

50,000,000 tokens ÷ (32 × 1024) = 1,526 steps
50,000,000 tokens ÷ (8 × 1024)  = 6,104 steps The token budget is fixed. A four-times-larger batch means a quarter as many optimizer steps.

Halving the gradient noise is worth something. Taking a quarter as many steps is worth more. The trade goes the wrong way.

This is the classic large-batch trade-off

Gradient error falls as √batch — sublinear. Step count falls as batch — linear. Beyond some point the linear loss always overwhelms the square-root gain.

These two runs sit on opposite sides of that point.

Two things that are not the cause

Throughput has nothing to do with it

Run 04 ran at 9,488 tokens/s against run 03's 10,231. That changes wall time and nothing else.

The optimisation trajectory depends on the step count and the learning-rate schedule. A slower machine does not produce a worse model — it produces the same model, later.

The learning rate was deliberately not scaled

Standard practice with a larger batch is to raise the learning rate, linearly or by √batch, because each step is more reliable and can afford to be bigger.

That was not done here, so the result is properly described as unscaled learning rate at 4× batch, not as "batch 32 is bad". Scaling the learning rate would have been a second change, and the run would no longer have isolated batch size.

What this actually says about reversibility

Reversibility did what it claimed. It cut peak memory 51.7% and reached a batch the baseline could not. The memory saving is real and measured.

But on this machine there was nothing useful to spend it on. Throughput falls with batch here, so the larger batch bought neither speed nor a better model.

Where this would go the other way

On a compute-bound device — a discrete GPU with idle arithmetic units — a larger batch raises throughput. There, reversibility's extra headroom converts into real speed, and the same experiment would report a win.

The finding is not "reversibility does not help". It is "reversibility helps when you are memory-bound, and this machine was bandwidth-bound instead".

Carry this forward: a bigger batch halves gradient noise and quarters the step count, so on a fixed token budget it loses; the memory saving was real but this hardware had no use for it.
